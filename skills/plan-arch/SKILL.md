# plan-arch - 架构设计

需求已经在 `spec.md` 里对齐完毕。你的职责是定下大体上怎么做 —— 用什么架构和结构，并落盘。

精度停在"大体运作逻辑"，不是逐行实现。

## 输入

先读 `docs/madousho/{YYYYMMDD}-{topic}/spec.md`，不要依赖对话上下文里残留的需求描述。

再跑 openspec-explore 粗略对齐代码库现状。项目若有既有的架构约束文档，例如 ADR、CONTEXT.md，一并读。

## 工作流程

1. 读 `spec.md` 与代码库现状
2. 需要时开 subagent 联网研究同类设计，把别人的取舍抽象出来给用户看
3. 逐项收敛六个问题：模块划分、模块职责、公开接口、模块间互动、数据流、业务流程
4. 用户显式确认后写入 `arch.md`，同时追加当天的决策记录
5. 可选：对用户担心的地方下钻，写进 `## 下钻`

每达成一次架构共识就立即追加决策记录，不要攒到最后补。架构讨论会反复推翻，事后还原不出当时为什么这么定。

## 输出

写入 `docs/madousho/{YYYYMMDD}-{topic}/arch.md`，与 `spec.md` 同目录。

```markdown
# {topic}

## 模块
每个模块的职责，以及对外暴露什么能力。用列表或 ASCII 树，能表达层次即可。

## 互动
模块之间怎么调用

## 数据流
数据从哪来、中途变成什么、最后存到哪

## 业务流程
有具体业务实现时才写，描述大概流程

## 下钻
只有被特别关注的地方才下钻到实现细节，其余保持上面的精度。
每一处写清为什么值得下钻，例如延迟敏感、流程敏感。

## 决策记录

### YYYY-MM-DD
- **定了** 结论 —— 依据
- **改了** 从 A 改成 B —— 原因
- **挂起** 悬而未决的问题
```

`定了` 的依据要写来源：代码库现状、联网研究的哪个案例、项目的哪条既有约束。架构决策的依据比结论更容易蒸发，而它是三个月后判断"这个决定是否还成立"的唯一凭据。

`改了` 必须写清被推翻的是什么。

## 规则

### 每轮开头报位置

每次回复的第一行输出当前位置：

`IDD · {topic} · {subtopic} · 正在谈：{当前问题}`

例：`IDD · user-login-system · 会话管理 · 正在谈：数据流`

`{subtopic}` 是 `spec.md` 划分出来的那几个部分里当前正在处理的一个。整个 topic 没有细分时省略这一段。

### 精度边界

- 停在大体运作逻辑，不进入逐行实现
- `## 下钻` 是唯一可以谈实现细节的地方

### 下钻由用户点名

只有用户说了担心某处，才对该处下钻。你最多提议「这里要不要下钻」，然后停下等回应。不要自己认定某处重要就开始扣细节。

### 推进需要显式许可

写入 `arch.md` 之前必须拿到用户的明确同意。列出待确认点，等用户回应。用户对方案提了意见不等于批准，改完之后仍需再次确认。

### 不重开需求

需求在 `spec.md` 里已经定稿。讨论中若发现需求本身有问题，停下来告诉用户，回到 plan-weaver，不要在这里顺手改需求。

## 完成标准

六个问题都有答案：模块划分、模块职责、公开接口、模块间互动、数据流、业务流程。

`下钻` 可以为空，没有特别担心的地方就不写。

写完 `arch.md` 后停下。不进入 plan 阶段，不调用 speckit。
