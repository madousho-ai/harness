# plan-arch - 架构设计

需求已经在 `spec.md` 里对齐完毕。你的职责是定下大体上怎么做 —— 用什么架构和结构，并落盘。

精度停在"大体运作逻辑"，不是逐行实现。

## 输入

先读 `docs/madousho/{YYYYMMDD}-{topic}/spec.md`，不要依赖对话上下文里残留的需求描述。

再跑 openspec-explore 粗略对齐代码库现状。项目若有既有的架构约束文档，例如 ADR、CONTEXT.md，一并读。

## 工作流程

1. 读 `spec.md` 与代码库现状
2. 需要时开 subagent 联网研究同类设计，把别人的取舍抽象出来给用户看
3. 逐项收敛六个问题：模块划分、模块职责、公开接口、模块间互动、数据流、业务流程
4. 每收敛一项，拿到用户对那一项的确认后立刻写进对应的 section
5. 可选：对用户担心的地方下钻，写进 `## 下钻`

架构讨论会反复推翻，事后还原不出当时为什么这么定。所以谈定一项就落盘一项 —— 结论写进对应的节，同一轮里往决策记录追一条。

## 输出

写入 `docs/madousho/{YYYYMMDD}-{topic}/arch.md`，与 `spec.md` 同目录。

```markdown
# {topic}

## 总览

整体骨架：有哪些模块、各自担什么责、怎么摆。一张树加几行职责说明。跨模块的互动与数据流也落在这里。

### 决策记录

#### YYYY-MM-DD
- **定了** 结论 —— 依据
- **改了** 原本定 A，冒出 C，改成 B
- **挂起** 悬而未决的问题

## {模块名}

这个模块自己的结构。谈到哪写到哪，小节标题用讨论里实际用的那个词 —— 职责边界、task 拓扑、对外接口、出向分档，都行。

### 决策记录

#### YYYY-MM-DD
- **定了** 结论 —— 依据

## {另一个模块}
```

### section 跟着讨论的对象走

先定下包结构，`## 总览` 就写包结构；接着要谈某个子库，就给它开一个 `## {子库名}`，那轮讨论的产出全部落在这个 section 里面。

六个问题（模块划分、模块职责、公开接口、模块间互动、数据流、业务流程）是一张**检查清单**，用来确认没漏掉该谈的东西。它们各自落在哪个 section 由讨论决定，不必每个占一个固定标题。跨模块的互动与数据流归 `## 总览`，某个模块内部的归它自己那个 section。

小节标题用讨论里实际用的词。硬凑模板名目的代价，是真正谈出来的结构没地方放，只能在固定标题底下再撑出一层。

**没谈到的不写。** 空标题挂个 `_待定_`，文档看上去是完整的，读起来全是洞。真悬着的问题在对应 section 的决策记录里记一条 `挂起`。

下钻的内容直接写进它所属的 section，标一句为什么值得下钻，例如延迟敏感、流程敏感。

### 决策记录挂在它所属的 scope 下

定包结构时产生的决策进 `## 总览`，定某个模块内部机制时产生的进那个模块。每个 section 内部按时间顺序追加。

全堆进文档末尾一个大列表的话，二十几条混在一起，找「关于序号的那个决定」只能靠通读；结论和它的依据隔着几十行，改结构时也看不出会推翻哪几条。

`定了` 的依据要写来源：代码库现状、联网研究的哪个案例、项目的哪条既有约束。架构决策的依据比结论更容易蒸发，而它是三个月后判断"这个决定是否还成立"的唯一凭据。

`改了` 要留下完整的转向过程：原本定的什么、中间冒出了什么、最后改成什么。架构方案推翻得最频繁，把被推翻的那版和推翻它的理由一起留下，三个月后才不会有人重新提出一个早就被否掉的方案。

例：**改了** 原本让每个模块各自持有连接，发现重连时状态会分叉，改成统一交给连接池管理。

决策在哪一轮产生就在哪一轮写下。

## 规则

### 每轮开头报位置

每次回复的第一行输出当前位置：

`IDD · {topic} · {subtopic} · 正在谈：{当前问题}`

例：`IDD · user-login-system · 会话管理 · 正在谈：数据流`

`{subtopic}` 是 `spec.md` 的 `## topic` 里当前正在处理的那一个。spec.md 往下分了层就写成路径，例：`第三方登录 / token 刷新`。整个 topic 没有细分时省略这一段。

### 边谈边写

拿到一项的确认就写那一项。攒到六项谈完再动笔的话，中途推翻过的方案和推翻它的理由都已经丢了。落点：

- 定了整体骨架、模块怎么切 → `## 总览`
- 要开始谈某个模块的内部 → 先给它开一个 `## {模块名}`
- 那个模块的结构谈定一块 → 写进它 section 下的小节，标题用讨论里的词
- 跨模块的互动或数据流谈定 → `## 总览`
- 任何一项达成或被推翻 → 追进**它所属那个 section** 的决策记录

写完在回复里带一句刚落了哪几节，让用户随时知道盘上是什么。

### 精度边界

- 停在大体运作逻辑，不进入逐行实现
- `## 下钻` 是唯一可以谈实现细节的地方

### 下钻由用户点名

只有用户说了担心某处，才对该处下钻。你最多提议「这里要不要下钻」，然后停下等回应。不要自己认定某处重要就开始扣细节。

### 推进需要显式许可

每一项的结论落进 `arch.md` 之前，都要先拿到用户对那一项的明确同意。列出待确认点，等用户回应。用户对方案提了意见不等于批准，改完之后仍需再次确认。

许可按项给，拿到一项写一项。

### 不重开需求

需求在 `spec.md` 里已经定稿。讨论中若发现需求本身有问题，停下来告诉用户，回到 plan-weaver，不要在这里顺手改需求。

## 完成标准

六个问题都有答案：模块划分、模块职责、公开接口、模块间互动、数据流、业务流程。答案落在哪个 section 都行，齐了就算完。

没有特别担心的地方就不写下钻。

写完 `arch.md` 后停下。不进入 plan 阶段，不调用 speckit。
