# 工具使用规则

下面说的是什么时候该想到哪个工具，具体怎么用见它们各自的 skill。

## 先挑工具，再动手

一件事有几种做法时，**从最专用的往最通用的挑**，命令行是这条梯度的末端。

三档大致是：

- **专用** —— 这个工具的存在理由就是这件事。查代码的调用链、按语法结构改代码、拿某个库的当前文档、抓一页网页的正文
- **半通用** —— 一类事都能干，具体怎么用要你自己拼。语义检索、搜索、自由写的 pattern
- **兜底** —— `bash` 和临时脚本。什么都能做，所以它永远是最后一个答案

**兜底那一档在你脑子里永远排第一。** 它出现在你见过的每一个例子里，专用的那个要主动想起来。这个不对称就是这条规则存在的全部理由 —— 单凭「哪个更合适」去判断，命令行每次都赢。

认工具**按它的说明认，别按名字认**。运行时会给工具名加前缀，同一个工具每个 session 拿到的名字都不一样，扫名字会漏掉。

### 每换一类动作，重新挑一次

接到活时挑一次，之后每跨过一道边界再挑一次：改代码转去查资料、查资料转去跑验证、跑验证转去写文档。开头那一套是按开头那件事挑的，走出三步早就不对口了。

### 一个信号：你正在写解析脚本

要写一段临时代码去**解析、提取、转换一种标准格式** —— HTML、AST、diff、日志、某个 API 的回包 —— 这几乎总是「有个专用工具你没想起来」的信号。停下来找一遍再动手。

这段脚本还带一层代价：它的正确性没人验过。抠错了不报错，只会安静地少给你几段，而你拿它当全部内容往下用。

## 代码探索

手上有这几样：

- `codegraph_codegraph_explore` —— 预先建好的代码知识图谱，一次调用拿回符号源码、调用链和影响面
- `cocoindex-code`（`ccc`）—— 语义检索，按意思找代码
- `ast-grep` —— 按语法结构搜索，也能做批量改写
- `grep` / `read` —— 文本匹配和精确读取

开放式的问题（这个功能怎么实现的、改这里会波及谁）先想到前两个，一次调用就能拿回结构化的答案，而且两边可以并行问。grep 加 read 的循环要几十次往返才够到同样的东西，中间翻进来的无关内容还会一直占着上下文。

宣布了要用某个工具就立刻发出调用 —— 没有 tool call 等于没做。

## 查外部资料

同一条梯度在工作区外面长这样：

- 某个库、框架、SDK、CLI 的当前用法 —— 有专门查文档的工具，先走它。你记得的那个 API 可能是两个版本以前的
- 手上有 URL，要它的正文 —— 有专门抓网页的工具，直接给你 markdown
- 手上没有 URL —— 先搜索拿到 URL，再抓正文
- 想看真实世界里别人怎么写这个调用 —— 有专门搜公开仓库代码的工具

`curl` 留给拿 JSON 的接口 —— 回包本来就是结构化的，抓下来直接读。**HTML 页面别走 curl**：抠正文那一步要么现写正则、要么现写解析脚本，而那正是上面说的信号。

## 跑命令

调用之前先估这条命令该跑多久，按估计设超时，**默认从 120 秒开**。测试、构建、git 操作绝大多数都在这个量级以内。估的时候一并问它凭什么结束 —— 结束的条件常常握在你自己手上，你刚写进去的那个输入、刚改掉的那一行，足以让一条本该几秒返回的命令再也不返回。

撞上超时，第一个要问的是这条命令本来会不会结束。dev server、file watcher、REPL、任何占着端口的东西都要等人来杀，超时开到二十分钟也只是换来更长的等待。这类要么换成会终止的形式（单次运行的 flag、`--watch=false`、build 代替 serve），要么让它彻底脱离这次调用的进程组、输出重定向到文件，起完立刻返回。

确认会自己结束的，一档一档往上抬并重跑：120 s → 240 s → 360 s → 480 s。

一上来就开十分钟二十分钟，真挂住的时候那一整段时间全赔进去，而「挂住」恰恰是最该早点知道的事。自己选的超时同时是一个预测，它跳了就说明你对这条命令的判断错了，两分钟知道比二十分钟知道好。

**起服务和后续操作不能塞进同一条调用。** 起长驻进程的那次调用必须自己就能返回，请求、探测、看日志全部放到后面独立的调用里发。塞在一起的话这次调用要等到服务退出才返回，而服务不会退出，于是整条命令超时报废 —— 探测结果没拿到，服务到底起没起来也不知道。

**同一条命令要跑很多次时，先跑一次什么都不改的，量出基线。** 超时按基线设，往上抬也从它起算，拍一个大数会让第一次撞上问题的那项赔掉整段时间。任何一项都无权终止整批：**等不到也是一种结果**，归类记下来，接着跑下一项。

**输出要留得下来，而且要边跑边留。** 命令的输出实时追加到文件里，攒在内存里的东西会跟着进程一起消失，前面几项白跑。批量跑的时候每一项**开工写一行、收工写一行** —— 只写收工那行的日志，卡住时恰好缺最要紧的那一条。有开工行，任何时刻 `tail` 一眼就知道跑到了哪一项、它已经等了多久；没有的话只剩翻进程树这一条路。

## 临时目录与副本

`/tmp/madousho-speckit/` 是你的工作目录，工作区之外的事全在这里面做。按 feature 分格，一个 feature 一格，格名取 `specs/` 下那个目录名：

```
/tmp/madousho-speckit/<feature>/
```

不属于任何 feature 的活，在根下自己建一格。

整棵树的副本用 `cp -a --reflink=auto <仓库> <副本>`：写时复制，带 `target/` 的大树也是秒级，占盘只有后来改动的那部分，构建缓存原样是热的。

**副本里的 `.git` 立刻处理掉。** linked worktree 的 `.git` 是一个**文件**，内容指回主仓库的元数据目录，`cp -a` 把它原样带过去，于是副本里任何一次 `git checkout` / `reset` / `stash` 写的都是真仓库的索引与 worktree 状态。用不上 git 就删掉它；构建要读 git 元数据的，把真 gitdir 整个拷一份进去顶上。

**同一棵副本里反复构建时，改完文件把 mtime 往前推。** 缓存是热的，构建系统按 mtime 决定重编哪些，还原之后忘了推的话，下一轮跑的仍是上一轮那份改动。

跑完删掉副本，日志留着 —— 写时复制的副本一重新构建就逐块解除共享，攒下来的是真实磁盘。

## 写文件

写之前先确认文件不存在，已存在就改用 edit。这个工作区有并发写者，用户和别的 session 可能正在同一棵树上动手，覆盖掉别人刚落的东西比漏写更难收拾。

## 改代码之前

把调用链、影响范围、相关实现先确认清楚。改完才发现波及了别处，代价比事先查这一趟高得多。
